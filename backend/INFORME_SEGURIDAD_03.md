# Tercera revisión de seguridad de SantolvDrive

Fecha: 23 de noviembre de 2026. Seguimiento de los riesgos RES-01 a RES-09 del [segundo informe](INFORME_SEGURIDAD_02.md). Esta revisión sustituye sus conclusiones pendientes para la versión actual; los informes anteriores se conservan como historial.

El usuario ha elegido **acceso solo local**, contraseña en Drive y **MFA de Pangolin al desplegar en el futuro**. No se ha publicado ningún servicio ni instalado un túnel. La API entrega datos; el HTML continúa en un listener estático separado. No se incorporan programas de ejecución adicionales, ASM ni Docker: los cambios son Rust, con PostgreSQL como excepción autorizada. `libc` y `windows-sys` proporcionan declaraciones Rust para funciones del sistema operativo.

## Correcciones y decisiones

| Riesgo anterior | Cambio aplicado y alcance |
|---|---|
| RES-01: publicación | Se mantiene la restricción local existente. Se conservan comprobación de Host, rechazo de cabeceras de proxy no configurado, CORS explícito y rechazo de `Origin: null`. Publicar mediante Pangolin queda expresamente aplazado: requiere configurar dominio HTTPS y confianza en el proxy antes de habilitar acceso remoto. |
| RES-02: contraseñas robadas | Se mantiene contraseña por decisión del usuario; no se introduce un segundo factor propio. Continúan Argon2id, espera progresiva por IP/cuenta, revocación y sesiones breves. Una contraseña robada sigue permitiendo autenticarse: el MFA futuro debe ser obligatorio en el acceso de Pangolin, sin rutas alternativas que lo eviten. |
| RES-03: bloqueo por IP compartida | El límite de 50 intentos/15 minutos se aplica al par IP + hash del usuario, y se limpia tras autenticar correctamente. Agotar el contador de una cuenta no bloquea el acceso de otra por compartir IP. Se conservan las esperas de hasta ocho segundos tras errores y el máximo de dos operaciones Argon2 simultáneas. Esto no elimina la saturación global bajo un ataque. |
| RES-04: enlaces y carreras de apertura | Lecturas, checksums y escrituras de bloques validan **el handle ya abierto**, antes de leer o modificar contenido. Se exige archivo normal y un único enlace duro; se rechazan symlinks y puntos de reanálisis. Windows y Linux comprueban además que el destino real del handle coincide con la ruta esperada; Linux requiere `/proc/self/fd`. Se normaliza la raíz al conectar. No se convierten todas las operaciones de nombres, creación, movimiento y borrado en operaciones sobre handles: sigue siendo obligatorio un volumen privado. |
| RES-05: cambios del HTML y XSS | El listener lee una copia limitada a 1 MiB al arrancar y no vuelve a leerla por petición. Cambiar el archivo mientras el proceso está activo no inyecta código en respuestas posteriores. Cada respuesta lleva nonce nuevo para scripts y bloques de estilo; CSP deja de admitir cualquier bloque CSS inline. Se permiten atributos de estilo porque la interfaz los utiliza. Para aplicar cambios legítimos del HTML hay que reiniciar el servidor. |
| RES-06: durabilidad | Los movimientos de contenido/directorios usan en Windows `MoveFileExW` con `MOVEFILE_WRITE_THROUGH`, conservando rutas largas y UNC sin conversiones de caracteres con pérdida. Unix mantiene sincronización de directorios en los puntos de publicación. Se conservan intención durable, estados y reconciliación. No se garantiza recuperar bytes destruidos por avería física ni se simula un corte eléctrico real. |
| RES-07: recursos y journal | Las 32 cargas pendientes se cuentan por usuario **entre todos sus espacios**, con bloqueo transaccional por cuenta e índice específico. Se limitan a dos las transferencias simultáneas por usuario y proceso, dentro de las ocho globales; el permiso de descarga dura hasta consumir/cancelar el cuerpo. El journal usa dos conexiones SQL reservadas y no compite por las 14 generales que mantienen las transacciones de publicación. Se retira la espera anterior de 250 ms. Los límites SQL y de adquisición siguen acotados; un PostgreSQL caído aún requiere reintentos de recuperación. |
| RES-08: mantenimiento | GitHub Actions añade ejecución manual y auditoría semanal, además de push y pull request. Mantiene acciones fijadas, credenciales no persistidas, permisos de lectura y `cargo audit --deny warnings`. La automatización detecta avisos publicados; no corrige ni certifica automáticamente dependencias futuras. |
| RES-09: cookies locales | Se conserva HttpOnly, SameSite Strict, ámbito `/api/v1`, CSRF y duración breve. HTTP sigue restringido a loopback; no se instala una autoridad de confianza en el equipo ni se aparenta aislamiento por puerto. El compromiso de la cuenta del sistema o de otro servicio localhost sigue fuera de la protección que ofrece una cookie HTTP. |

## Validación realizada

- `cargo test --locked`: **49 pruebas activas correctas en Windows**, 26 unitarias y 23 de integración contra PostgreSQL aislado. Tres pruebas de aprovisionamiento y una medición de carga continúan excluidas de la suite ordinaria.
- Pruebas específicas: enlaces duros rechazados sin modificar bytes, preservación de rutas Windows/UNC/caracteres nativos, HTML inmutable y nonce de estilos, límite de una cuenta sin bloquear otra por la misma IP, presupuesto de cargas entre varios espacios y journal disponible con el pool general agotado.
- Pruebas HTTP reales del ejecutable: autenticación cookie/bearer, recuperación de sesión y CSRF, rechazo de origen opaco/ajeno, API sin HTML, archivos originales, subida binaria, descarga íntegra, papelera, restauración, eliminación física y administración exclusivamente por consola.
- Comprobaciones del cliente HTML con Node, sin navegador ni capturas. No se ha realizado revisión visual ni una matriz de compatibilidad de navegadores.
- `cargo fmt --check` y `cargo clippy --locked --all-targets -- -D warnings` correctos. El entorno de compilación avisa de que copia la caché incremental cuando no puede crear enlaces duros; no es un fallo del análisis del código.
- `cargo-audit 0.23.0`: **0 vulnerabilidades y 0 advertencias conocidas**, 282 dependencias; RustSec con 1.563 avisos, commit `52384ab5581a4487b62c549eef95cf7ba7e8bad5`. No se añadieron excepciones para ignorar avisos.

## Límites que siguen siendo reales

1. **No hay garantía de seguridad con el sistema operativo comprometido.** La cuenta del servicio, los binarios, el HTML de arranque, la configuración y el volumen deben permanecer privados. Procesos con los mismos permisos pueden modificar la instalación; los administradores del sistema controlan sus datos. En Unix distinto de Linux no se realiza la comprobación de padres mediante `/proc/self/fd`; no se certifica un volumen compartido hostil en ninguna plataforma.
2. **No hay garantía de disponibilidad frente a todo DoS.** Intentos distribuidos, nombres de usuario aleatorios, clientes lentos o varios usuarios hostiles pueden consumir CPU, conexiones, IO o filas temporales de limitación. Hay presupuestos, cuotas, timeouts y limpieza, pero falta medir el límite real del servidor de destino. Los límites de concurrencia en memoria son por proceso: no se presentan como coordinados entre varios servidores.
3. **No hay recuperación de bytes físicamente perdidos.** No se generan backups ni historial por decisión de producto. El journal recupera operaciones interrumpidas cuando sus datos siguen intactos; no sustituye una copia independiente ni una prueba de apagado en hardware real.
4. **Una XSS desconocida o una extensión maliciosa aún puede actuar en el origen autorizado.** HttpOnly protege la lectura del identificador de sesión; no impide que código ejecutado en el origen realice operaciones. No deben añadirse scripts externos ni inserciones HTML con contenido de usuario sin revisar.
5. **El acceso público y MFA están aplazados por elección expresa.** No abrir puertos ni desactivar validaciones para conectar un túnel. Antes de publicar se necesitan dominio dedicado, HTTPS, cookie Secure, configuración concreta de proxy y comprobación de que Pangolin exige MFA a todos los usuarios previstos.

Estas limitaciones no se declaran corregidas por haber añadido límites o pruebas. La revisión no demuestra ausencia de fallos desconocidos ni constituye una auditoría independiente.
